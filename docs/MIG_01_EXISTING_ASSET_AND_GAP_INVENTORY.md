# MIG-01 Existing Asset and Gap Inventory

## 1. Scope

This inventory closes `MIG-01.1`: identify the current importer, fixture corpus, acceptance transaction, activation, browser evidence, export path, and known debt before changing product behavior.

It distinguishes four evidence levels:

1. original/runtime-produced data;
2. synthetic schema fixtures;
3. background/package integration tests;
4. packaged real-browser journeys.

A module existing at one level does not prove the complete migration parent journey.

## 2. Current pipeline

```text
File or online text
  -> importZeroOmegaBackup
  -> LegacyImportCandidate + report + secretMaterials
  -> LegacyImportPanel compatibility review
  -> accept-import command
     -> secret snapshot
     -> secret writes
     -> Draft replacement
     -> rollback Draft/secrets on accept failure
  -> separate apply command
     -> validate / compile / install / confirm
     -> preserve or restore previous Applied/runtime state on apply failure
  -> active browser state
  -> exportZeroOmegaBackup
  -> schemaVersion:2 backup
```

The UI presents “导入并立即使用” as one action, but the implementation currently composes two commands: `accept-import`, then `apply`.

## 3. Existing original and synthetic corpus

### Original/runtime-produced positive fixture

`fixtures/zeroomega-v2/original-default-v3.5.0.bak`

- provenance: generated by the pinned official ZeroOmega v3.5.0 runtime/package;
- integrity metadata exists in `original-default-v3.5.0.provenance.json`;
- contains original schema-v2 settings, `proxy`, `auto switch`, bypass rules, startup and Quick Switch settings;
- safe synthetic endpoint values were used during original runtime generation.

Current use:

- importer unit-level round trip;
- exporter unit-level round trip.

Not currently proven for this fixture:

- packaged browser import and activation;
- real URL routing;
- browser restart recovery;
- browser-level semantic re-export and re-import;
- failure injection across the complete transaction.

### Synthetic positive fixtures

The repository includes fixtures for:

- minimal profile families;
- conditions and results;
- nested Switch and Virtual references;
- Rule List and AutoProxy variants;
- PAC and local-file cases;
- credentials and redacted headers;
- Unicode/IDN/IP conditions;
- unknown metadata;
- operational settings and update state.

These fixtures provide broad schema and semantic coverage but were authored as controlled test data. They do not substitute for an owner-representative daily-use export or additional original-runtime-produced complex exports.

### Negative fixtures

The repository includes malformed encoding, missing references, cycles, excessive nesting, oversized input, unsupported profile/result/condition shapes, secret-like metadata, unsafe local PAC, unsupported SOCKS credentials, and other bounded rejection cases.

This is a strong parser and mapping foundation. The negative cases still need to be connected to complete active-state preservation evidence.

### Missing corpus

No previously uploaded or repository-committed owner-representative daily-use `.bak` has been found.

The current positive original corpus lacks:

- real complex nested Switch/Virtual/Rule List output from the original runtime;
- real PAC/update/cache/authentication metadata output from the original runtime;
- a sanitized owner daily-use configuration.

## 4. Importer assets

`packages/legacy-zeroomega` currently provides:

- JSON, base64, and object input handling;
- size, nesting, and graph bounds;
- stable internal IDs;
- profile and condition mapping;
- reference resolution and cycle checks;
- capability analysis;
- secret extraction into separate material;
- inactive candidate creation;
- deterministic compatibility reports;
- preservation of selected safe opaque metadata;
- target-dependent, downgraded, preserved, ignored-generated, ignored-runtime, and rejected outcomes.

### Importer gaps to verify or correct

- There is no explicit top-level `unsupported` or `unknown` status in the current result taxonomy; these meanings may be compressed into `rejected` or issue codes.
- Alias color and identity preservation require real-data verification.
- Virtual mappings currently include downgrade paths that must be tested against original semantics.
- Unknown behavior-like fields are rejected; the exact boundary between safe opaque preservation and behavior-changing rejection needs a field matrix.
- AutoDetect is target-dependent and requires browser evidence.
- `monitorWebRequests` and related operational settings require mapping review against the no-global-listener architecture.
- The official default `.bak` is too simple to expose many of these gaps.

## 5. Acceptance transaction assets

`packages/profile-workflow/src/import-acceptance.ts` provides a bounded transaction for accepting an import candidate:

- snapshot affected secrets;
- write secret material;
- replace the Draft;
- restore prior Draft and secret state when acceptance fails.

This is a useful, correctly isolated transaction.

### Transaction boundary gap

The ordinary “import and use” journey is not one background transaction. It is:

1. accept imported secrets and Draft;
2. separately apply that Draft.

If Apply fails:

- the previous active Applied/runtime state is protected or restored;
- the imported Draft and accepted secret material remain present.

This may be a valid safe-editing outcome, but it is not yet proven to match the original import contract or the user expectation created by “导入并立即使用”. The required decision is not simply “always roll back Draft”. It must be based on original behavior, recovery usability, precise error state, and the direct-migration contract.

## 6. Apply and activation assets

The Apply pipeline already separates:

- validation;
- compilation;
- persistence;
- browser installation;
- confirmation;
- Applied revision update;
- rollback/recovery.

Current tests cover many injected failures and preserve the previous active configuration.

### Activation gaps for MIG-01

- no complete official `.bak` acceptance-to-activation integration test;
- no complete owner-export activation evidence;
- no single migration transaction/result object covering accept plus apply;
- no explicit assertion of the intended Draft/secret state after Apply failure during import;
- no real-export large-storage capacity evidence;
- no complete two-browser migration failure matrix.

## 7. Browser evidence assets

### Chromium

`scripts/e2e-chromium.mjs` performs a packaged-browser import journey using synthetic `minimal-profile-types.json`:

- choose backup file;
- display compatibility check;
- click “导入并立即使用”;
- observe success;
- export schema-v2 content;
- verify major profile types and absence of secret references;
- reload and re-import the first exported file;
- export again.

This is meaningful browser integration evidence.

It does not prove the official original `.bak`, an owner export, a browser restart after migration, or semantic route equivalence for the real imported corpus.

### Firefox

`scripts/e2e-firefox.mjs` serves synthetic `minimal-profile-types.json` through the online-backup path and exercises Firefox extension/runtime behavior. Current inventory confirms online restore analysis and broad runtime coverage, but does not establish a complete official-original import, activation, restart, semantic export, and re-import chain.

### Browser gap summary

The project has browser import infrastructure, not zero browser import coverage. The missing proof is **real/original corpus through the complete parent journey on both targets**.

## 8. Export assets

`exportZeroOmegaBackup` produces plain schema-v2 content and maps major profile families, operational settings, Quick Switch, startup, PAC, Rule Lists, bypass, conditions, and safe opaque metadata.

Existing tests prove:

- synthetic representative import/export/import equality;
- official default `.bak` import/export/import equality at the candidate level;
- omission of credentials and sensitive headers;
- preservation of several Nex-only extensions through namespaced metadata.

### Export gaps

Warnings or omissions exist for:

- proxy credentials;
- sensitive request headers;
- disabled Nex-only state;
- regex flags;
- PAC and AutoDetect fallback extensions;
- independent Rule List intervals;
- other state that original schema-v2 cannot represent directly.

These are not automatically defects. MIG-01 must classify each as:

- required exact original data;
- safe security omission;
- namespaced opaque preservation;
- target-dependent behavior;
- Nex-only extension outside original semantic equivalence;
- unsupported with precise warning.

Candidate-level equality does not prove original-runtime usability or effective route equality after export.

## 9. Current strongest conclusions

1. The importer/exporter foundation is materially stronger than the previous progress narrative implied.
2. There is one authentic original-runtime-produced `.bak`, not zero.
3. There is packaged Chromium import/export/re-import coverage, not zero browser import coverage.
4. Most broad compatibility evidence still uses synthetic fixtures.
5. The official original `.bak` has not been driven through the packaged full chain.
6. No owner-representative daily-use backup is currently available.
7. Active-state safety on Apply failure is protected, but the complete “accept import + apply” transaction and post-failure Draft/secret contract are unresolved.
8. Semantic export is broad but requires a field-level classification and real/original runtime proof.

## 10. First implementation slice

The next authorized implementation slice is `MIG-01.2A`:

> Drive `original-default-v3.5.0.bak` through importer analysis, import acceptance, Apply using the workflow runtime test harness, semantic export, and re-import in one integration test.

The test must assert:

- original default `proxy` and `auto switch` identity, colors, order, rules, bypass, startup, and Quick Switch settings;
- secrets and Draft are committed only through acceptance;
- Apply reaches the expected Applied/runtime state;
- export remains schema-v2 and re-imports to the same required user intent;
- a forced Apply failure preserves the previous active state and explicitly asserts the intended imported Draft/secret outcome.

This slice does not yet claim browser completion. It creates one deterministic background transaction oracle before extending the same official `.bak` into Chromium and Firefox packaged journeys.
